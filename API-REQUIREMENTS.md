# Backend API Requirements

What the backend has to implement to replace mock mode. Generated by reading the actual frontend implementation — `js/api-client.js` (the endpoint list), `js/mock-data.js` (the mock router, which doubles as a request/response spec), and the `data/*.json` fixtures (exact field shapes) — not from the `Prompts/` planning docs. **If this document and the frontend code ever disagree, the code is the source of truth; update this document to match.** See "Divergences from `Prompts/05-backend-api-design.md`" at the bottom for where the original design doc is stale relative to what's actually built.

## Conventions

- Base path: `js/config.json`'s `apiBaseUrl` (currently `/api`). Every call goes through `apiFetch()` (`js/utils.js`).
- **Auth: cookie-based, not a bearer token.** `apiFetch` sends `credentials: "include"` and never reads/attaches an `Authorization` header — the backend must set an `HttpOnly` session/JWT cookie on login and read it on every subsequent request. A `401` on any call other than `/auth/me` or `/auth/login` redirects the browser to `login.html`.
- Request/response bodies are JSON. `GET`s never send a body; query params are appended by the caller where needed (`toQuery()` in `api-client.js`).
- **Response envelope the frontend expects:** every call resolves to `{ok, status, body}`. On `!ok`, `api-client.js` throws `Error(body.summary)` with `.status` and `.body` attached — so **error bodies must be `{"summary": "human-readable message"}`**, not the `{error, message, fields}` shape `05-backend-api-design.md` originally proposed. Field-level validation errors have no dedicated shape in the current frontend — they're shown as the one `summary` string.
- Dates are `"YYYY-MM-DD"`; timestamps are unzoned `"YYYY-MM-DDTHH:mm:ss"` local-time strings (see every fixture below) — not ISO-8601 with an offset.
- **No pagination on any list endpoint.** Every `GET` list call returns a plain JSON array; filtering (employee/date/status/etc.) happens client-side in the page script against the full array. If a real dataset makes "return everything" impractical, that's a backend-and-frontend joint change, not something to bolt onto the API unilaterally — see `02-database-schema.md`'s pagination convention in `Prompts/`, which the frontend doesn't yet consume anywhere.
- Multi-tenancy: not implemented in this frontend yet (single implicit org). See `Prompts/13-multi-tenancy.md` for the intended direction — out of scope for this document.

## Auth & session

| Method | Path | Body | Response | Notes |
|---|---|---|---|---|
| POST | `/auth/login` | `{orgUsername, email, password}` | `{}` (cookie set on response) | Generic failure — frontend shows "Invalid credentials." regardless of the actual error. `orgUsername` is the org-username field on `login.html` (lowercase, `^[a-z0-9_]{1,64}$`) — see `Prompts/multi-tenancy.md`. Mock mode (`js/mock-data.js`) doesn't validate it yet. |
| GET | `/auth/me` | — | **Session object**, see below | Called on every authenticated page load (`auth-guard.js`) and right after login. `401` → redirect to `login.html`. |
| POST | `/auth/change-password` | `{currentPassword, newPassword}` | `{}` | Voluntary password change — no page currently calls this (a future `settings.html` control is the intended consumer; `change-password.html` and the `forcePasswordReset` flag that used to drive it have been removed, since no path ever assigns an employee a password to be forced to change). |
| POST | `/auth/set-password` | `{token, newPassword}` | `{}` ok; `400` `{summary}` | Unauthenticated — the invite-link landing page (`set-password.html?token=...`, emailed when HR creates an employee via `/directory` or `/hr/employees`, see below). `400` on a bad/expired/already-used token or a password failing policy. On success it sets `password_hash` and **establishes a session** (same posture as `/auth/login`) — `set-password.js` calls `apiClient.me()` right after and lands on `dashboard.html`; since that session's `directoryProfileComplete` is false, `auth-guard.js` immediately hands it to `complete-profile.html` (see `directoryProfileComplete` below). |
| POST | `/auth/logout` | — | `{}` | Called by `complete-profile.js` after a successful save (deliberately ends the session so the employee signs in fresh), and by `js/loader.js`'s header sign-out control. |
| POST | `/auth/resend-verification` | — | `{}` | Re-sends the verification email to the current session's user. Called from `profile.html` ("resend verification email" link, shown only when the session's `emailVerified` is `false`). Rate-limit server-side; always return `{}` even if already verified (no enumeration / no error surface). |
| POST | `/auth/forgot-password` | `{orgUsername, email}` | `{}`; `404` if org unknown | Unauthenticated. Emails a reset link pointing straight at `reset-password.html?token=...` (`app.reset.link-base`, no backend hop); the token is validated only on `/auth/reset-password`. `200 {}` whenever the **org** exists — regardless of whether the *email* matches an account (no email enumeration; `forgot-password.html` shows one neutral "if that email is registered…" message). `404` when the **org username** is unknown — same enumeration surface `/auth/login` already exposes; the page then shows "That organization was not found." |
| POST | `/auth/reset-password` | `{token, newPassword}` | `{}` ok; `400` `{summary}` | Unauthenticated, and unrelated to `/auth/set-password` above despite the similar shape — this is the *forgot-password* recovery path for an employee who already has a password, not first-time invite onboarding. `400` on bad/expired token or a password failing policy (`js/password-checks.js` mirrors the rules). Called by `reset-password.html`; on success it points the user to `login.html`. |
| POST | `/employees/me/directory-profile` | Same personal/address/emergency-contact/phone fields as directory's P2-P4 (below), minus identity/employment/pay | `{}` ok; `400` `{summary}` | Authenticated. Called once by `complete-profile.html`, the page `auth-guard.js` hands an employee to while `directoryProfileComplete` is false. `400` on the same all-or-nothing address/emergency-contact rules the directory wizard enforces (`js/directory-profile-rules.js`). On success sets `directoryProfileComplete = true` (one-way — it never re-flips false). |

**Session object** (`GET /auth/me`, and `GET /employees/me` returns the identical shape):

```
{
  id, employeeCode, name, email, phone, address, role,     // role: "EMPLOYEE" | "HR"
  managerId, department, designation, employeeType,        // employeeType: "REGULAR" | "INTERN"
  dateOfJoining, dateOfExit, basicSalary, status,           // status: "ACTIVE" | "ON_NOTICE" | "EXITED"
  isManager,           // computed: true if anyone's managerId points at this employee
  managerName,         // resolved display name, or null
  directoryProfileComplete,  // boolean — false only for an employee who has used the set-password
                             // link but not yet saved complete-profile.html; auth-guard.js hard-redirects
                             // there until it succeeds. true for the org-creator (signup) and for anyone
                             // who has already completed it. Use === false, not falsy — a backend that
                             // hasn't shipped the field yet must not gate every session.
  emailVerified,       // boolean — false shows the dashboard banner + profile "Not verified" / resend link
  organizationName, organizationKey,  // organizationKey is the org's login/URL slug (navbar org display); JSON field name must stay camelCase regardless of the backend's DB column name
  address1, address2, city, landmark, postalCode, state, country  // read-only here, see below
}
```

The seven structured-address fields, plus the personal-tier fields (`dateOfBirth`, `gender`, `nationality`, `maritalStatus`, `bloodGroup`, `personalEmail`) and the emergency-contact triplet (`emergencyName`, `emergencyRelationship`, `emergencyPhone`), mirror the directory's HR-entered `employee_sensitive` data (§ Employee Directory). They are **employee-writable exactly once**, only through `POST /employees/me/directory-profile` above, only while `directoryProfileComplete` is false. Everywhere else — ordinary `PATCH /employees/me`, or after the gate is satisfied — they stay read-only from the employee's side; only an `ORG_ADMIN` can edit them, via `/directory`. They exist alongside the separate free-text `address` column, which stays the only field the *ordinary* self-service form (`PATCH /employees/me`) can write. `country` is an ISO 3166-1 alpha-2 code.

`isManager` is **not** a stored role — `role` only ever holds `EMPLOYEE`/`HR` (matches `Prompts/02-database-schema.md`). It must be computed server-side (`EXISTS (SELECT 1 FROM employee WHERE manager_id = :id)`) and included on every session response, since `auth-guard.js` and most manager-only page scripts branch on it directly.

**Leave type object:**
```

Codes in use: `CL`, `PL`, `OPTIONAL_HOLIDAY`, `MARRIAGE`, `MATERNITY`, `PATERNITY`, `SABBATICAL`, `LOP`, `INTERN_STUDY`, `PUBLIC_HOLIDAY`.

The maternity situation-type sub-classification (`requiresSituationType` on the leave type, `situationType`/`expectedDeliveryDate` on apply) has been **dropped entirely** — no `SituationType` enum, no column, no field anywhere server-side. Do not reintroduce it from the mock layer or old docs.

**Apply payload** (`POST /leave-requests`, built by `js/leave-request-form.js`):
```
{ leaveTypeId, startDate, endDate, reason }
```

**Leave request object** (summary rows drop `approvals`/`reason`/HR fields; detail includes everything):
```
{
  id, employeeId, employeeName, leaveTypeId, leaveTypeCode, leaveTypeName,
  startDate, endDate, numDays, status, reason,
  isHrImposed, hrNotes,          // present only on HR-imposed LOP rows

## Employee Directory

Backs `directory.html` / `js/api/directory.js`. Specified in full in `Prompts/employee-directory.md`; this section is the wire contract the frontend already calls. **`GET`/`POST`/`PATCH`/`DELETE` are implemented server-side** (`DirectoryController` → `DirectoryFlow`) — see "Columns that do not exist yet" below for what's still a gap.

Read is open to **any authenticated session**; there is no role gate on `GET`. What varies is the *scope*, which must be resolved server-side from the JWT and the manager graph and **never** from a request parameter:

| Caller | Scope | Sees |
|---|---|---|
| `ORG_ADMIN`, `HR` | `ORG` | every non-`EXITED` account in their own org |
| has ≥1 direct report (derived from `employee.manager_id`; there is no `MANAGER` role) | `REPORTS` | their direct reports only |
| plain `EMPLOYEE` | `SELF` | their own row only |

Writes are **`ORG_ADMIN` only** — `HR` has no write access here and keeps using `/hr/employees` above.

| Method | Path | Payload | Response |
|---|---|---|---|
| GET | `/directory` | query: `page`, `size` (default 50, **max 200**), `department`, `managerId`, `search` | Spring `Page` of **directory objects**, below |
| POST | `/directory` | Create payload, below | `{id}` |
| PATCH | `/directory/{id}` | Same shape, `email` ignored | Single directory object |
| DELETE | `/directory/{id}` | — | `{}` |

**Directory object — two tiers, and the split IS the access control.**

Base (P0/P1), returned to anyone who can see the row at all — including a manager viewing a direct report and an employee viewing themselves:

`id`, `employeeCode`, `name`, `email`, `phone`, `department`, `designation`, `employeeType`, `status`, `dateOfJoining`, `probationEndDate`, `managerId`, `workLocation`, `gradeBand`, `costCenter`, `shiftTimezone`, `previousEmployer`, `skills`, `certifications`, `training`, `mentor`, `education`, `assetIds`, `licenses`, `badgeNumber`, `linkedIn`, `bio`

Sensitive (P2–P4), returned **only to an `ORG_ADMIN`**:

`dateOfBirth`, `gender`, `pronouns`, `nationality`, `maritalStatus`, `bloodGroup`, `personalEmail`, `languages`, `hobbies`, `address1`, `address2`, `city`, `landmark`, `postalCode`, `state`, `country`, `emergencyName`, `emergencyRelationship`, `emergencyPhone`, `basicSalary`, `bankAccount`, `bankIfsc`, `nationalId`, `taxId`, `passport`, `visaStatus`, `ethnicity`, `veteranStatus`, `disabilityStatus`, `religion`, `healthNotes`, `unionMembership`

**`ORG_ADMIN` is a stricter test than `ORG` scope, and the difference matters.** An `HR` also resolves to `ORG` scope. Gating the sensitive tier on scope instead of role would hand HR every employee's bank details, national ID and health notes. Gate on the role.

`role`, `dateOfExit`, `emailVerified` and the legacy free-text `address` column are on **neither** tier and must never appear — they are account lifecycle, not directory data. `js/directory-scope.test.js` asserts the exact key set for both tiers, that the two lists never overlap, and that twelve named sensitive fields are absent without the admin flag; widening either list fails the frontend tests.

`bankAccount`, `nationalId`, `taxId` and `passport` are displayed masked to their last 4 characters even for an `ORG_ADMIN`. A full-value reveal should be its own audited endpoint (spec Phase 4) and does not exist yet.

Work anniversary, birthday (month/day, year withheld), skip-level manager, and the assembled address/emergency-contact display lines are all **derived client-side** — do not add columns or response fields for them.

**Create payload:** every writable key from the object above except `id` and `status`. Notably **absent, each on purpose**: `password` (a roster endpoint must not carry a credential — mint one server-side and send the verification mail), `role` (hardcoded `EMPLOYEE`), `status` / `dateOfExit` (account lifecycle; `DELETE` is what sets `EXITED`), `basicSalary` (settable only via a later `PATCH`). `employeeCode` and `dateOfJoining` may be omitted — default to `EMP-<hex>` and today. Address and the other Steps 4/5/6/9 sensitive fields **are** accepted on create (`DirectoryFlow.create` applies them to the row right after it's persisted) — only `basicSalary` is create-excluded.

**PATCH semantics:** `null` means unchanged, except **`managerId`, where an explicit `null` clears the manager** (the form has a real "No manager" option, so detaching has to be expressible); an absent key still means unchanged. `email` is ignored if sent — it is the sign-in identity and needs the conflict handling `/hr/employees` has.

**Required error responses**, which the UI already branches on:

- `403` on a `managerId` filter from a non-`ORG` caller — **fail closed, do not silently drop the filter**
- `403` on any write from a non-`ORG_ADMIN`
- `404` (not `403`) for a target outside the caller's org — a `403` would confirm the row exists
- `400` on deactivating your own account — without it an org admin can lock themselves out
- `400` on a self-referencing or cross-org `managerId`, and on a longer manager cycle (A→B→A), which the client cannot detect
- `409` on a duplicate email within the org

`DELETE` is a soft, idempotent delete: `is_active=false`, `status=EXITED`, `date_of_exit=today`. Nothing is hard-deleted, so leave and appraisal history keeps its foreign keys.

**Columns that do not exist yet.** Real today: `employeeCode`, `name`, `email`, `phone`, `designation`, `department`, `employeeType`, `status`, `dateOfJoining`, `managerId`, `workLocation`, `basicSalary`, plus the full Steps 4/5/6/9 sensitive set (`dateOfBirth`, `gender`, `pronouns`, `nationality`, `maritalStatus`, `bloodGroup`, `personalEmail`, `languages`, `hobbies`, the seven address columns, the three emergency-contact columns, `bankAccount`, `bankIfsc`, `nationalId`, `taxId`, `passport`, `visaStatus`, `ethnicity`, `veteranStatus`, `disabilityStatus`, `religion`, `unionMembership`, `healthNotes`). **Still a Phase 2/3 gap:** `probationEndDate`, `gradeBand`, `costCenter`, `shiftTimezone`, `previousEmployer`, `skills`, `certifications`, `training`, `mentor`, `education`, `assetIds`, `licenses`, `badgeNumber`, `linkedIn`, `bio`. The frontend sends and renders all of them and the mock layer persists them, but `DirectoryForm`/`DirectoryData` don't carry this second group yet — a real `POST`/`PATCH` silently drops them (`@JsonIgnoreProperties(ignoreUnknown = true)`) and `GET` never returns them.

**Structured address.** Seven columns (`address1`, `address2`, `city`, `landmark`, `postalCode`, `state`, `country`), never one free-text blob. `country` is ISO 3166-1 alpha-2, upper-case, never a typed country name. `city` is required and is deliberately not in the source spec's field list — no postal format works without one. Required-ness is enforced Java-side only, since `hbm2ddl.auto=update` cannot add a `NOT NULL` column to a populated table. `postalCode` and `state` are conditionally required for a short country set (US, CA, IN, GB, AU, BR) rather than a ~250-row matrix nobody maintains. ISO 3166-2 subdivision codes are **not** enforceable from the JDK, so `state` is stored as typed. There is no normalised `postal_code_norm` column: addresses appear on no search surface, so there is nothing to index yet.

**Voluntary fields are voluntary.** `ethnicity`, `veteranStatus`, `disabilityStatus`, `religion`, `unionMembership` and `healthNotes` must never be required, never inferred, and never defaulted. Note the spec's requirement that EEO answers be "never visible to anyone with hiring/comp authority" **cannot be met in this build** — an `ORG_ADMIN` *is* the comp authority and no `EEO_REPORTING` role exists. That clause needs the Phase 6 RBAC work; do not report it satisfied.

**Create/update employee payload** (`hr-employees.js`):
```
{ employeeCode, name, email, phone,
  dateOfJoining, dateOfExit,        // dateOfExit: null if not set
  employeeType,                     // "REGULAR" | "INTERN"
  designation, department,
  managerId,                        // number or null (top of hierarchy)

  status }                          // "ACTIVE" | "ON_NOTICE" | "EXITED"
```
No password field at all, on create or update — every employee this endpoint creates gets `password_hash = NULL` and a set-password invite email queued to the same mailer `/auth/forgot-password` uses, pointing at `set-password.html?token=...` (`POST /auth/set-password`, above). This is the same no-password model `/directory`'s create already documents; `hr-employees.js` used to collect a typed temporary password plus a `forcePasswordReset` flag, and both have been removed from the form and this payload.

| POST | `/hr/employees/import` | `{rows: [...]}` — parsed client-side from an uploaded CSV/TSV, one object per row: `{name, email, role, managerEmail}` | `{created, skipped: ["reason", ...]}` |

(`hr-employees.js`'s `bulk-upload-form` sends **one** `POST /hr/employees/import` call carrying every row, not one `POST /hr/employees` per row.) `managerEmail` is resolved to `managerId` server-side, falling back to no manager if unmatched or blank. A row with a blank or non-`EMPLOYEE`/`HR` `role` fails JSON body parsing and **voids the whole batch** — verified against the endpoint directly, not per-row-skipped. Every created row gets `password_hash = NULL` and a queued set-password email, same as a single `POST /hr/employees` create — there is no temporary-password/credentials-download step for bulk rows either.

## Appraisals

State machine (drives which buttons/forms each page renders — see `js/appraisal-status.js`):
```
SELF_APPRAISAL → MANAGER_REVIEW → HR_REVIEW → CALIBRATION → FINALIZED → ACKNOWLEDGED → CLOSED
                                        │↕RETURNED (manager re-edits, back to HR_REVIEW)
FINALIZED/ACKNOWLEDGED/CLOSED → REOPENED → FINALIZED (re-finalize)
any non-terminal status → CANCELLED (terminal)
```

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/appraisals/me` | — | Array: `[{id, cycleName, status, selfRatingLabel, managerRatingLabel}]` |
| GET | `/appraisals/{id}` | — | **Appraisal detail**, see below |
| POST | `/appraisals/{id}/self-review` | `{selfRatingValueId, selfComments, selfCategories}` | `{}` — moves status to `MANAGER_REVIEW` |
| GET | `/appraisals/team` | — | Array: `[{id, managerId, employeeId, employeeName, cycleName, status}]` — the manager's direct reports' reviews |
| POST | `/appraisals/{id}/manager-review` | `{managerRatingValueId, managerComments, managerCategories}` | `{}` — moves status to `HR_REVIEW` (same target whether first submission or a `RETURNED` re-submission) |
| POST | `/appraisals/{id}/advance-to-calibration` | — | `{}` — `HR_REVIEW → CALIBRATION` |
| POST | `/appraisals/{id}/finalize` | — | `{}` — `CALIBRATION → FINALIZED` or `REOPENED → FINALIZED` |
| POST | `/appraisals/{id}/return-to-manager` | `{reason}` (required) | `{}` — `HR_REVIEW → RETURNED` |
| POST | `/appraisals/{id}/reopen` | `{reason}` | `{}` — from `FINALIZED`/`ACKNOWLEDGED`/`CLOSED` → `REOPENED` |
| POST | `/appraisals/{id}/cancel` | — | `{}` — from any non-terminal status |

| PATCH | `/appraisals/{id}/calibrate` | `{calibratedScore, calibrationReason}` | `{}` or `400 {"summary": "..."}` **if `calibratedScore` differs from the computed manager score by more than 0.005 and no `calibrationReason` was given** — this validation must be server-side, not just client-side |
| POST | `/appraisals/goals` | `{cycleId, employeeId, description, status: "NOT_STARTED"}` | `{id}` |
| PATCH | `/appraisals/goals/{id}` | `{status}` (only field the UI ever sends) | `{}` |

**Appraisal detail** (`GET /appraisals/{id}`):
```
{
  id, cycleId, employeeId, employeeName, managerId, status,
  snapshot: { name, email, department, designation, managerName, organization, dateOfJoining },
  // ^ frozen at roster-import time — must NOT be re-derived live from the employee record on read,
  //   so a later department/manager change doesn't retroactively rewrite an in-flight/closed review
  cycleName, cycleCategories,        // the cycle's category template, for seeding a fresh editor
  ratingValues,                       // full appraisal_rating_value catalog, embedded so the page
                                       // never has to make a second call to render the dropdown
  performanceLevels,                  // full performance-level bands, same reason
  selfRatingValueId, selfComments, selfCategories,
  managerRatingValueId, managerComments, managerCategories,
  goals: [{id, description, status}],
  returnReason, reopenReason,         // present only after the corresponding transition
  calibratedScore, calibrationReason, // present only once HR has calibrated
  selfScore, managerScore, finalScore // SERVER-COMPUTED, see "Score computation" below — never sent by the client
}
```

**Category node shape** (`selfCategories`/`managerCategories`/`cycleCategories`, arbitrarily nested):
```
{ id, name, weight,          // weight: percent (0-100), meaningful only at the top level
  score,                      // 1-5 or null
  comment,
  subsections: [ ...same shape... ] }
```

**Score computation (must be replicated server-side exactly, per `js/eval-categories.js` + `js/mock-data.js`):**
- `averageScore(node)` = mean of every non-null `score` found on that node and all its descendants (a section can be scored directly as a leaf, or purely via its children — same formula either way).
- `weightedCategoryScore(categories)` = Σ over top-level nodes with a non-zero `weight` of `averageScore(node) * weight/100`; `null` if no top-level node carries a weight or none of the weighted ones have a score yet (unweighted/legacy cycle).
- `selfScore` = `weightedCategoryScore(selfCategories)` — informational only, deliberately never run through the performance-level lookup (structurally maxes out below 100% since it has no "Manager Overall Assessment" component).
- `managerScore` = `weightedCategoryScore(managerCategories)` **plus** `(rating value's numeric `value` for `managerRatingValueId`) * 0.1` — the standard schema reserves the un-weighted 10% for the single overall rating field, added on here rather than modeled as its own category (avoids double-counting the manager's overall judgment against their own category scores).
- `finalScore` = `calibratedScore` if HR has set one, else `managerScore`.
- `performanceLevelFor(score, levels)` = the level whose `[minScore, maxScore]` contains `score` (`Prompts`' bands: 4.5–5.0 Exceptional, 4.0–4.49 Exceeds, 3.0–3.99 Meets, 2.0–2.99 Partially Meets, 1.0–1.99 Does Not Meet — HR-configurable, don't hardcode these).

## Divergences from `Prompts/05-backend-api-design.md`

That doc was written as an early design pass and hasn't been kept in sync with the actual frontend build-out. Where they conflict, **this document (grounded in the real `api-client.js`/`mock-data.js`) is correct**:

1. **Approve/reject is one endpoint, not three.** `05` proposes separate `POST /manager/leave-requests/{id}/approve`\|`/reject` and `POST /hr/leave-requests/{id}/approve`\|`/reject`. The actual frontend has exactly one: `POST /leave-requests/{id}/action` with `{action}`, used identically by the employee, manager, and HR pages — the server must resolve who's allowed to act from the request's current pending step, not from which URL prefix was hit.
2. **Error body shape differs.** `05` proposes `{error, message, fields}`; the frontend only ever reads `body.summary`.
3. **No pagination anywhere.** `05` proposes `?page=&size=` + a `{content, totalElements, totalPages}` envelope on list endpoints; every actual list call returns a bare array and every page filters/paginates it client-side (see the client-side pagination just added to `manager-team-requests.html`'s "Leave requests" table).
4. **`05` is missing two entire modules**: One-on-Ones and Appraisals (including cycles, rating values, performance levels, calibration, roster import) don't appear in it at all — both are fully built in the frontend and documented above.
5. **HR employee CRUD is built**, not "not yet built" as `Prompts/flow.md` states — `hr-employees.html` has a full add/edit form, CSV bulk-upload, and a manager-reassignment tool, all wired to real `apiClient` calls. `flow.md` is stale on this point specifically; impose-LOP and HR-override genuinely are still unwired, as both docs agree.
6. **Notification "mark read" doesn't exist** in the frontend (`05` proposes `POST /notifications/{id}/read`) — see the Notifications section above.
